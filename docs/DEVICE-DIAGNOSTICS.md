# 设备诊断与兼容性取样

这项功能用于排查设备问题、收集新型号的能力定义，为后续支持音箱、人体传感器、门铃等设备提供依据。

## 用户如何反馈

1. 先在 MijiaDeck 中复现问题。
2. 摄像头或灯光控制页点击“诊断报告”；其他设备从主界面右上角菜单进入“设备诊断报告”，选择对应设备。
3. 等待报告生成，点击“复制诊断报告”，粘贴到 GitHub Issue。
4. 补充期望功能、操作步骤、实际现象和米家 APP 中是否正常。固件版本若显示为空，可手动从米家 APP 补充。

仅生成报告不会操作设备，也不会上传报告。“打开反馈页面”只打开 GitHub 新建 Issue 页面，需要用户自行粘贴和提交。

## 报告包含什么

- 程序版本、Windows 版本与系统架构。
- 所选设备的型号、规格 URN、在线标记、云端服务地区，以及列表中可获得的固件版本。
- 从公共 MIoT 规格获取的服务、属性、读写和通知能力、数值范围和枚举定义，以及动作的输入输出、事件的参数定义。
- 摄像头最近一次在本程序内的连接尝试：阶段、阶段耗时、错误编号、HTTP 状态码、云端错误码、实际返回的视频供应商编号、授权字段是否齐全、是否收到视频帧和画面尺寸。

取样时只请求所选型号的公共规格；不会批量读取设备当前属性或执行动作，也不会主动申请视频授权。摄像头的协议信息来自用户正常播放时实际取得的响应；未尝试播放时可能未知。音箱、门铃、传感器等设备的规格取样均可从主界面进入，即使当前没有专用控制页。

不包含账号凭证、Token、密钥、签名原文、设备 DID、MAC/IP、设备名称、家庭和房间名称、媒体地址、画面、当前传感器读数或历史活动记录。代码从明确的字段白名单生成报告，禁止直接序列化设备、API 对象、请求响应或异常文本。

## 维护者如何解读

`schema: mijiadeck-device-diagnostic/1` 是结构版本；报告使用 Markdown 包裹 JSON，可直接贴到 Issue。

能力定义与实测结果分开：`capabilities.declared_only` 始终为 true。存在 `notify` 或事件定义，仅表明设备声明了这项能力，不代表程序已订阅、收到事件或具备可用的历史记录接口。型号相同、固件不同也可能有差异，不应只凭元数据宣称完全兼容。

`observation` 当前主要记录摄像头视频链路。`NOT_ATTEMPTED` 表示没有视频连接尝试；`NONE` 表示本次尝试尚未记录错误，仍需结合 `video_received` 判断是否出画面。视频供应商编号 4 被当前后端解释为 CS2；其他编号保留数值并标记为 unrecognized，不猜测它的协议。

自 v1.1.2 起另外记录 `video_codec`（实际媒体包报告的 H264/H265）和 `gop_bootstrap`（本地组件是否启用了首个关键帧回放）。播放器错误按资源读取、格式、网络、权限分别记录为 `PLAYER_RESOURCE`、`PLAYER_FORMAT`、`PLAYER_NETWORK`、`PLAYER_ACCESS`；不再把所有播放器错误统称为解码失败，也不记录可能包含媒体地址的任意错误文本。

公共规格请求超时或不可用时，报告会注明原因并使用已有 SDK 缓存。SDK 缓存不保留事件、通知及动作参数的完整定义，相关字段会明确标为不可获得；缺少数据不能解释为设备没有该能力。

生成时间与最后一次连接尝试的相对耗时都写入报告。切换账号或重启后，摄像头连接取样不会作为历史日志永久保存。报告可以用于补充型号兼容性证据，但实际控制与视频播放仍需用户实机验证。
